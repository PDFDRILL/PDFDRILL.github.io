questions this report keeps raising

Why MathPix.

The honest version, including where it loses. Every number below comes from a document on this site, not from a vendor deck.

Why is every row here read by MathPix rather than by something free?

Because without MathPix this page could not exist — not “would be worse”, could not exist. A row needs three things together: the recognised LaTeX, a confidence in that LaTeX, and the crop the reading came from. Remove any one and the report collapses.

Without the confidence there is no way to pick 57 equations worth reviewing out of 1,219 — you are back to reading all of them. Without the crop there is nothing to measure the render against, so the residual column is undefined. MathPix lines.json is the only format we have found that ships all three per equation.

The alternatives do not fail at this; they are not built for it. pdfminer.six reads an embedded text layer and performs no recognition at all — no confidence, no crop, no LaTeX. Tesseract gives a per-word confidence but emits text, not math. Neither is a bad tool. Neither is the tool this report is made of.

Is MathPix actually more accurate, or just better packaged?

Measured, on the same eight-page document, three routes:

8
pdfminer.six
One Paragraph per page. A whole page of prose and LaTeX run together in a single blob. Not empty — structureless.
119
tesseract
Finely split, uniformly flat: Paragraph and Table, nothing else. The most nodes, the least document.
79
mathpix
Fewer nodes, and the only route that sees what the document is about: 24 Diagram, 9 Formula, 2 Picture, 1 Toc.

MathPix returns fewer elements than OCR and wins anyway. Counting nodes measures how hard a route chopped the page, not how much of the document it understood.

The full comparison, with the element trees side by side, is in the text-layer section of the main site.

What does this report say about MathPix’s confidence score?

That it is conservative, which is the useful direction to be wrong in.

Of 1,219 equations, MathPix rated 57 below 0.5 — under 5% it was unsure about. inkdrill then measured 55 of those against the scan independently, knowing nothing about the confidence value. Eleven of the 55 came back clean or noise: pixel distance 0–7, component delta 0–1. Indistinguishable from the scan.

Roughly one in five equations at the very bottom of MathPix’s own confidence scale render correctly anyway. It under-rates itself.

That costs review time and nothing else. The opposite error — high confidence on a wrong reading — is the one that quietly corrupts a corpus, and it is why the two instruments here are reported side by side and never averaged into a single score.

Where does MathPix lose?

The annotation layer, and it loses badly.

A paper’s page one says “Our code is available here”, where here is a hyperlink with no separate anchor text. MathPix returns the sentence. The URL is simply not in the output — not truncated, not mangled, absent. So is it absent from MathPix Markdown, from plain extraction, and from a chatbot PDF upload. An LLM reading any of those cannot answer “where is the code?”, because on the evidence it has been given, there is no code.

pdfdrill links reads the annotation layer directly and answers in about 50 ms, with no key and no network. Details in the invisible-link section.

Best OCR is not the same as only tool. The right architecture is a cheap keyless command that answers what it can, escalating to a paid call only when it genuinely cannot — which is the whole design of this toolkit.

Keyless routes are free. Isn’t paying for a key a waste of money?

Keyless is not free. It is billed somewhere else — in render time, in tokens, and above all in your hours.

pdfdrill ships the keyless path and takes it seriously: pdfdrill ocr renders pages through tesseract into a MathPix-compatible lines.json, and with no key at all the prompt-driven sub-tasks route to whichever Claude is already driving the session. The output is byte-identical to the keyed API path. It works.

It is also, for steady use, slower and more expensive. Delegating a whole document to a running model burns more wall-clock and more tokens than one keyed call. The invoice says zero; the calendar does not.

The real cost of the free route is not the compute. It is the engineering afternoon you spend making it produce something the paid route hands you in a single response — and then spend again next month, because nothing you did was durable.

Set against MathPix pay-as-you-go, that is not a close call for anyone whose time has a price.

Does any of this depend on the vendor answering the phone?

Yes, and this turns out to be the part nobody benchmarks.

Over the life of this project I have written to MathPix, MinerU, pdfminer and Tesseract with real questions about real documents.

MathPix Admin has answered every time, inside 24 hours. From the other three I have never received a reply of any kind.

There is a nice irony in the sample. This site hosts MinerU’s own paper as its translation example — arXiv 2409.18839, drilled, element-typed, and machine-translated into Portuguese, sitting in the artifacts section next to everything else. I have still not heard back from them.

To be fair to the volunteers: the pdfminer and Tesseract maintainers owe nobody a reply. They publish excellent code for free and are not anyone’s support desk. That is exactly the point. A key does not only buy an endpoint — it buys a counterparty. When the pipeline breaks at midnight against a document that matters, the question is not which repository has more stars. It is whether there is a person on the other end whose job it is to answer.

Across every document on this site, exactly one of them has been.
